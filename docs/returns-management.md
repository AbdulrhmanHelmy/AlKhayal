# Unified returns management

The Returns section has two visible entries: `returns-overview` (إدارة المرتجعات) and `return-details` (تفاصيل المرتجع). Details can also open by clicking a saved return or after successful posting. Opening details directly provides a searchable saved-return selector; selecting a different return refreshes only its detail view and ignores stale responses. Separate `sales-returns` and `purchase-returns` screens are hidden compatibility redirects. Both renderers are enabled in the shell's completed-route list and tested through the actual dispatcher.

## Workflow and money

Sales and purchase invoice lists now show an additional `مرتجعة جزئيًا` or `مرتجعة بالكامل` badge beside the original posting status. List and invoice GET responses expose `hasReturns`, `isFullyReturned` and computed `returnStatus` (`none`, `partial`, `full`). Read projections derive these flags from saved return lines: every original line's quantity must be returned for a complete return; posted purchase returns alone count. Classification is quantity-based, not based on rounded money totals. Historical returns are included automatically. No invoice posting status, document, balance or schema is rewritten.

Management lists the latest 200 matching real sales/purchase returns, sorted by UTC creation time, with search by return number, original invoice number or party name. Adding a return starts with an invoice type and exact posted invoice number. It loads only the invoice's eligible lines, remaining quantities and original serial/IMEI choices. Sales returns require a reason; purchase returns offer cash reimbursement or supplier-account settlement. The unified flow uses the original invoice warehouse. Server-side FIFO/provenance/serial/quantity validations remain authoritative. Ambiguous purchase invoice numbers across suppliers are rejected rather than selecting an arbitrary invoice.

For a sales cash refund, the current operator policy (2026-10-29) withdraws only from `مرتجعات البيع` and permits its balance to become negative for that refund. It never resolves, funds from or updates `إيراد الوردية`. Credit-invoice returns reduce the customer account debt first, capped at the current debt so it cannot go below zero; any remainder is refunded in cash, including amounts collected on the general account without an invoice-linked payment. For example, a return of 100 against remaining debt of 30 reduces the debt by 30 and refunds 70. Deposits can replenish a negative returns balance; ordinary manual/purchase/supplier withdrawals retain their no-overdraft rule. Existing transfer history remains immutable and visible.

A purchase return in `cash_refund` mode deposits the recorded reimbursement in `مرتجعات الشراء`. `supplier_credit` retains supplier-account settlement without inventing cash. Existing supplier payable/credit and inventory/FIFO return rules remain unchanged. Named returns cashboxes are provisioned/reused transactionally on the first cash refund, reject duplicate names, banks with the same name or reserved-code conflicts, and retain a stable account ID thereafter. No manual treasury permission is granted by return posting.

Details display original invoice/party, warehouse, operator, local display time, reason, returned lines/units/serials, exact total/cash/account adjustment and linked treasury directions/amounts. Historical returns remain readable and explicitly show no treasury source link when posted before this integration. No historical cash is backfilled. Posted returns are not edited or deleted through this UI.

## Architecture and schema

`Application.Returns.ReturnService` normalizes lookup/read contracts through `IReturnReadStore` and the existing Sales/Purchase services; `SqliteReturnReadStore` provides bounded parameterized queries. `ReturnsController` translates the authenticated HTTP contract to existing Application return commands. Original sale/purchase posting endpoints also use the new shared treasury writer, so direct callers cannot skip the cash effects. Actor-bound operation hashes/replay checks continue to precede writes.

Additive migration `030_returns_management.sql` creates immutable `ReturnTreasuryAccounts` identity links and `ReturnTreasuryLinks` with real nullable sales/purchase-return foreign keys, exactly one source family, unique movement and per-return-role identity. Treasury ledger/audit/version, refund movements, source links, return documents, FIFO/physical stock, customer/supplier projections and sales payment changes commit together. Any failure rolls everything back, including newly provisioned accounts. Cash sale posting retains its existing independent shift-revenue destination. Monetary display/requests retain two digits over exact scale-4 storage; quantities retain scale 6.

The shell accepts optional route state when navigating to a contextual detail tab; selecting another return replaces the existing detail identity before render. `return-details.permissionRoute` points to `returns-overview` so it shares the parent screen grant. Server checks require the same management grant for all unified endpoints. No framework/package/runtime target changed; JS remains compatible with Chromium 109. Native visual/DPI and Windows 7 runtime qualification were not performed.

## HTTP contract

All `/api/returns` routes require a session and effective `returns-overview` access (administrators retain full access). POST additionally requires CSRF. Standard `{ success, data, error }` envelopes are used.

- `GET /api/returns?search=`: latest 200 records with type (`sales`/`purchase`), return/original invoice identities, party, warehouse, actor/time and exact financial summaries. Sales/purchase IDs may overlap; type is always part of identity.
- `GET /api/returns/invoice?type=sales|purchase&number=...`: exact posted invoice lookup with available lines/serial/IMEI choices. Missing/canceled/draft invoices return 404; ambiguous purchase numbers return 400.
- `GET /api/returns/{type}/{id}`: complete saved detail, lines/serials and linked treasury movements. Missing IDs return 404; invalid type returns 400.
- `POST /api/returns`: `{ type, invoiceId, operationKey, reason?, returnMode?, lines:[{ invoiceLineId, quantity, units:[{ serial, imeis:[] }] }] }`. Sales requires a reason; purchase uses `cash_refund` or `supplier_credit`. Success/replay returns 201 `{ type, id }` for detail navigation. Invalid input returns 400, posting/funds/quantity conflicts 409, and logged unexpected SQLite failures 503 with a same-request retry instruction.

The frontend preserves drafts/pending operation identities across tab changes, blocks duplicate submits and freezes uncertain payloads for retry. Definitive 4xx errors release fields; stale lookup/list/detail responses are ignored.

The list endpoint intentionally reads optional `search` query text at the HTTP boundary rather than binding it as a simple string action parameter. Web API rejected explicit `?search=` as invalid model state, causing the initial/cleared list to display `بيانات غير صالحة`. Real HTTP regression coverage now exercises omitted, empty and whitespace search before data exists and cleared search after posting. Mutation model-state/CSRF checks are retained.

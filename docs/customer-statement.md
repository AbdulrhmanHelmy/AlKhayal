# Customer statement and account operations

The Customers section exposes `customers-list` and `customer-statement` only. `customer-credit-payment` is a hidden compatibility redirect to the statement; its separate payment form is no longer an operational destination. Customer management stays unchanged.

The real statement reads `/api/customers` and `/api/customers/{id}/statement`. A persistent customer selector and date filters sit above debt and movement details. The screen shows current debt across all dates, opening balance for the selected period, period increases, collections/reductions and closing balance. Movements retain actual document references and saved notes. Filtering to older dates does not present an old period closing balance as the customer's current debt. There are no mock records or unavailable-invoice preview controls.

The existing `/api/customers/{id}/transactions` endpoint powers two contextual dialogs: `increase` (إضافة مديونية) and `collection` (تحصيل من العميل). Inputs use positive decimal text with at most two decimals, local business-date defaults and saved notes. An increase may exceed the previous debt. Collection cannot exceed the current server-validated debt. Each dialog keeps one operation key, blocks repeated submissions, locks inputs during posting and uncertain retries, and resubmits the exact original command after a lost response. Definitive validation failures retain editable inputs. Success reloads the statement without remounting selectors/date filters; a movement outside the selected dates is explained in the success notification.

Application validation and the existing SQLite writer transaction remain the financial boundary. Transaction entry, idempotency identity and customer balance projection commit together or roll back. The projection now checks overflow before inserting an increase. Current debt comes from the exact ledger aggregate; no historical entries are changed. Manual statement collection updates the customer account ledger only: this task does not create a treasury deposit or allocate payment to sales invoices. Sales invoice-specific payment/refund workflows retain their existing boundaries.

The old frontend statement referenced `context` without receiving it, causing loading to fail. Renderer dispatch now supplies the real render context and request-generation/active-route guards prevent late responses repainting another customer/page. The old all-time SQL reader initialized its running balance with the sum of every movement, then added every movement again. It now starts an unfiltered statement at zero; a date-filtered statement starts with entries strictly before `from`. `currentBalance` is independently derived from the same full ledger rows, and `notes` is exposed on movements. The schema is unchanged and no migration is required.

The statement GET and transaction POST require an authenticated session and effective `customer-statement` screen access for cashiers; POST also requires CSRF. Administrators retain access. Stored old-route permissions are not silently expanded to the new combined workflow. Historical operation-key ownership/conflict behavior is unchanged. Numeric overflow returns an Arabic validation envelope; logged SQLite failures return 503 and the client keeps retry identity.

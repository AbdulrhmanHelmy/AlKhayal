# Supplier accounts

The Suppliers operational section now contains only `suppliers-list` (unchanged supplier directory) and `supplier-payment`, renamed to حسابات الموردين. Other supplier routes remain registered as hidden redirects to `supplier-payment`, preserving saved links without exposing extra pages. Quick access targets the canonical accounts route.

Accounts uses a persistently mounted supplier name/code/phone search and server pages of ten suppliers. A supplier dropdown lets the operator choose which account to display. No invoice request is sent before selection; only the selected supplier card and its invoices/actions are loaded. Changing selection replaces the displayed account, and clearing selection hides its details. The selection survives successful addition/payment refreshes and workspace rerendering while present in the current supplier page. A request token prevents late previous-supplier results from repainting the active account. The selected card shows actual payable and credit, invoices, add-debt-invoice and account-payment actions. Invoices show their source type, date, total, paid, returned, remaining, and state. Purchase drafts are explicitly labeled and cannot be paid. Legacy account invoices and integrated purchase invoices have separate identities even when their numeric IDs match; payment requests supply exactly one of `invoiceId` or `purchaseInvoiceId`.

The requested increase is a **new debt invoice**, not editing an existing invoice. The dialog records invoice number (optional/generated), date, optional due date, exact positive total and notes. It explicitly explains that this records debt only and creates no stock receipt. Supplier invoice creation, the immutable ledger entry and the payable/credit projection commit in one SQLite transaction. Existing supplier credit is consumed before creating new payable. A failure rolls back all writes. No new table or migration is needed: this uses `SupplierInvoices` and the existing `SupplierLedgerEntries.SupplierInvoiceId`, `OperationKey` and `RequestHash` columns.

The API accepts an optional `operationKey` for backwards compatibility; the new UI always supplies it. The Application service hashes length-prefixed supplier/number/date/due-date/exact-scaled-total/notes/actor fields. A matching ledger operation returns the same invoice with `replayed: true`; a changed request, actor, supplier or operation type returns `409 operation_conflict`. Actor attribution is retained in the immutable ledger description. Concurrent identical requests create one invoice. The UI disables repeated saves; an uncertain network/5xx result locks the fields and retains the same command/key for verification by retry.

Invoice reads expose `documentStatus` and `returnedAmount`. Remaining is `max(0, total - paid - returned)`, including posted purchase returns. Invoice payment eligibility applies the same returned-value deduction and the supplier's overall payable cap. Payments on account now allocate to invoices by earliest due date (invoice-date fallback), then original creation time. Paid/remaining fields include those allocations without double-counting explicit invoice payments. All new HTTP payments withdraw from a required treasury account in the same supplier transaction; see [supplier-payment-treasury.md](supplier-payment-treasury.md). Cash purchase posting keeps its separate real treasury integration from migration 025.

The invoice union query reads monetary values as invariant decimal/integer text, then converts them exactly in C#. This avoids provider-dependent Dapper casts when SQLite returns different numeric types for legacy and purchase rows, and avoids REAL-based amount arithmetic in this read path. Historical rows and posted purchases are not rewritten.

## Validation

`SupplierAccountsTests` verifies new-debt persistence, concurrent replay/conflicting keys, source-invoice ID collisions, independently allocated payments, supplier credit consumption, late-ledger-failure rollback, purchase-return remaining balances and overpayment rejection. `SupplierAccountsApiTests` exercises authenticated HTTP creation, CSRF rejection, decimal-text input, replay/conflict, payment and persisted invoice reads after new service construction. `frontend/tests/supplier-accounts-tests.js` executes the production renderer/modal handlers for grouped suppliers/invoices, draft nonpayment, both invoice ID families, addition retry identity and locked inputs, refresh/search node retention, empty/retry states, stale navigation and the two-entry sidebar/hidden redirects.

Commands: `dotnet build AlKhayal.slnx --no-restore -m:1`, `dotnet test AlKhayal.slnx --no-restore -m:1`, `node --check frontend/js/modules/renderers.js`, and `node frontend/tests/run-tests.js`. Tests use disposable SQLite files; no operator database is mutated. The frontend keeps the existing RTL/theme/form primitives, bounded local table scrolling and Chromium 109-compatible JavaScript. Native WebView2 visual/DPI and actual Windows 7 acceptance remain separate checks.

Results on 2026-10-28: the full solution build passed; the full suite passed 167 integration and 49 unit tests, then the additional supplier HTTP test passed independently (217 tests in total). The full frontend suite passed for 101 routes, including the new grouped-accounts handlers; JavaScript syntax and diff whitespace checks passed. Initial integration failures exposed mixed SQLite numeric provider types in the combined invoice query; exact text-based materialization resolved both regressions before the successful rerun. NuGet vulnerability metadata was unavailable (`NU1900`). Stored screen grants are retained; access to the canonical accounts page uses `supplier-payment` rather than automatically expanding old hidden-route grants.

The 2026-10-28 supplier-picker UI correction passed `node --check frontend/js/modules/renderers.js`, the complete `node frontend/tests/run-tests.js` suite and `git diff --check`. Handler regressions cover no eager invoice loading, exactly one selected account, selection clearing, switching, stale previous-supplier responses and selection retention after writes. This frontend-only change does not modify API/database behavior or require a migration; native visual verification remains separate.

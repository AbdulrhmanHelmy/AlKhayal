# Product catalog

## Implemented scope

Phase 2 Tasks 2.1–2.2 provide a real SQLite-backed catalog for products, nested categories, units, configurable attributes/values, variants, SKUs, barcodes, and exact rational product-unit conversions. Products support name, optional description/category, base unit, `stock`/`service`/`non_stock` type, scale-4 non-negative sale price, nullable scale-4 non-negative reference purchase price, active state, archive state, migration-review state, timestamps, and optimistic `Version`. A default internal variant is created automatically for simple products; it remains hidden as an incomplete configuration until identifiers or variant settings are requested.

The Arabic RTL UI reuses the approved shell and components. The list supports server-side search, category/status filtering, bounded paging, edit, and administrator state/archive actions. Product Catalog is the primary visible entry; add, quick-add, and edit routes remain valid contextual/deep-link flows. Category and unit management are discoverable from the catalog and use full-width searchable tables with `+ إضافة تصنيف` / `+ إضافة وحدة قياس` actions. Create and edit use the shared compact centered modal form (inline validation, save loading state, guarded unsaved close, focus return, and no duplicate listeners); status can be activated/deactivated, while deletion is not exposed. Administrators can create a category beside the form selector without losing the mounted draft; successful creation refreshes the selector and chooses the new row. Product edit exposes capability assignment, attribute values, variant identifiers, barcode lookup, and exact unit conversion inputs; stock quantities and warehouse balances are deliberately not product-master fields and are read from the inventory ledger instead (see Task 2.4 below).

Product capabilities are shown as Arabic RTL switches under `خصائص المنتج`. The switch list is projected from the canonical FeatureRegistry/effective-feature response, so global availability is separate from the product assignment: new products start with all optional switches off, while an existing assignment remains visible as read-only when its global feature is later disabled. Sizes and colors reveal ordinary free-text rows rather than a predefined catalog picker; users can add, edit, or remove rows before the single product save. `product-variants` is an internal dependency and is never exposed as a switch. The aggregate command resolves normalized free-text values, assigns the internal capability, and creates the size/color Cartesian combinations inside the same SQLite transaction as the product, prices, assignments, and audit record. IMEI requests serial tracking and expiry requests batch tracking. Tracking switches configure product requirements only; serials, IMEI, batches, expiry values, and stock movements are created exclusively by the Phase 2.4 inventory ledger when an inventory document is posted, never by the product save (see Task 2.4 below).

The product form has compact basic fields, optional switches with size/color inputs directly beneath them, and one Save/Cancel footer. A globally disabled, unassigned property has no control or placeholder. An existing assignment disabled globally is retained with a read-only historical marker. The selected basic unit supplies the canonical exact `1/1` product-unit row even when Multiple Units is off; enabling Multiple Units adds only optional conversion rows. Create sends all product information, free-text values, variant combinations, identifiers, and unit mappings as one retry-safe aggregate request. An unsuccessful request leaves the draft mounted; workspace-tab redraws restore the session draft. Changing the base unit of an already saved product is rejected until a dedicated, reference-safe conversion workflow exists.

The paginated catalog returns one row per product ID. Its list DTO includes ordered saved size/color values, active variant count, and persisted expiry/serial/IMEI configuration flags. SQLite loads summaries for the page in two bounded queries, including historical assignments after a global feature is disabled. The name cell shows compact badges for real values and configuration; a simple product shows no badges. Edit renders saved free-text values and maps variant value IDs back to human-readable size/color labels, SKU, and active barcode. Unchanged combination IDs are reconciled against stored combination keys. New combinations receive new IDs; removed unreferenced combinations are archived. Removing a combination with any SKU or barcode history is rejected transactionally with an Arabic explanation. Existing separate product IDs are never merged.

## Money and legacy data

Catalog sale price is stored in `ProductDetails.SellPriceScaled` as `long` at scale 4. Reference purchase cost is stored in nullable `ProductDetails.PurchasePriceScaled` using the same scale. `NULL` means unknown, especially for pre-hotfix products; it is never silently converted to verified zero and is not an inventory average cost. API values are strings such as `"12.3400"`. C# parses invariant decimals, performs checked multiplication by 10,000, rounds midpoint away from zero once, and rejects negative or overflowing values. Display precision remains a General Settings concern.

Migration 008 never drops or rebuilds `Products`. Valid legacy rows retain IDs, names, and original prices and receive details/default variants. Invalid legacy rows are retained, quarantined inactive with `review_required`, and recorded for administrator review; activation is blocked until a valid edit resolves the issue. `CatalogOperations` makes product creation retry-safe by operation key and request hash.

## Task 2.2 persistence and boundaries

Migration 010 adds product attributes, values, assignments, product units, variants, variant attribute combinations, SKUs, and barcode history. SKU and active barcode values are globally unique; variant combinations are unique per product; retired barcodes remain historical and cannot be used for lookup. Conversions use positive integer numerator/denominator pairs and are reduced/validated in the Application/Data boundary. Capability assignment is checked against effective feature state, while existing assignments remain readable when an administrator disables a capability. Barcode lookup is scanner-ready, authenticated, CSRF-free for reads, and still reports inactive/archived reasons without inventing inventory quantities.

## Deliberate limitations

Task 2.2 did not implement real warehouses, quantities, reorder levels, tracking identities/receipts, ledger movements, purchasing, or sales posting, and it added only product-level tracking configuration switches. Phase 2.4 (see below) now ships SQLite-backed warehouses, the immutable stock-movement ledger with its balance projection, batch/serial/IMEI identity records, and the operational `دليل المخازن` directory at route `warehouses-list`; the compatibility routes `warehouse-add`, `stock-adjustment`, `warehouse-transfer`, and `stock-movements` redirect to that directory, which reads real warehouse rows rather than a mock dataset. Still deliberately out of scope: reorder levels and reorder alerts, purchasing and supplier documents, sales/POS posting, FEFO lot auto-allocation, and negative stock. Weighted-average valuation of outbound stock exists only inside the inventory ledger; the catalog purchase price stays a reference value and is never substituted for an actual acquisition cost. A tracking switch alone still creates no tracking record or stock movement. The remaining contracts are planned in `phase-2-architecture-blueprint.md`; inventory balances are derived from the Task 2.4 immutable ledger and must never be edited directly.
# Inventory integration in Task 2.4

Inventory attaches to the existing `ProductVariants.Id` and `ProductUnits.Id`. The catalog purchase price remains a reference, not recorded acquisition cost. Warehouse quantities and weighted-average value are queried from `/api/inventory/balances` and are not editable product master fields. Tracking assignments remain enforced after posting history, including when global availability changes. The catalog row and compact badges remain unchanged; see [inventory-ledger.md](inventory-ledger.md).

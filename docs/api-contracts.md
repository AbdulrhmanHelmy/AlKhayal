# API contracts

Sales return posting may now make the sales-returns cashbox negative. For credit invoices it reduces current customer debt first (never below zero), then refunds the residual cash, including general-account collections. This changes existing return behavior without changing request contracts. Other withdrawal endpoints retain no-overdraft rules. See [sales-refund-overdraft.md](sales-refund-overdraft.md).

Purchase/sales invoice GET and list responses include `hasReturns`, `isFullyReturned` and `returnStatus` (`none` / `partial` / `full`), derived from persisted return quantities without changing `status`. See [returns-management.md](returns-management.md).

`/api/returns` now exposes the unified persisted list/post contract, `/invoice` exact original-invoice lookup and `/{type}/{id}` detail. Session, `returns-overview` permission and mutation CSRF are enforced. Sales cash returns withdraw only from the sales-returns cashbox without touching shift revenue; purchase cash returns deposit into the purchase-returns cashbox. See [returns-management.md](returns-management.md).

Sales invoice/list/post responses expose nullable `treasuryAccountId`, `treasuryAccountName` and `treasuryMovementId`. Cash posting automatically deposits in the shift-revenue cashbox in the same transaction; POS permission suffices without manual treasury access. See [sales-shift-revenue.md](sales-shift-revenue.md).

`/api/expenses/categories` supports GET/POST for saved types; `/api/expenses/vouchers` supports GET/POST for immutable idempotent expense documents with selected treasury withdrawals. Session/screen checks protect reads and writes; CSRF protects mutations. Full contracts: [expenses.md](expenses.md).

Unauthenticated first-run routes are limited to `GET /api/auth/bootstrap-status` and `POST /api/auth/bootstrap`. Status returns `{ required: true|false }`. Bootstrap accepts only `{ username, password, confirmPassword }`; the server fixes the role to `administrator`, requires a nonblank password with matching confirmation, atomically requires an empty `Users` table, and returns the normal session cookie on success. Any existing active or inactive user makes the POST return `409 bootstrap_unavailable`.

New monetary request fields accept invariant decimal text with at most two fractional digits. Quantity fields keep their existing scale-6 contract. Catalog price DTOs and formatted purchasing/inventory financial fields use two display digits; scaled integer fields remain scale 4 for exact auditing. Finalized invoice and supplier-account totals use nearest-piastre, midpoint-away-from-zero rounding.

Product configuration accepts `batch-tracking`, `expiry-dates`, `serial-numbers`, and `imei-tracking` in `capabilityKeys`. Application automatically includes batch when expiry is selected and serial when IMEI is selected. Catalog summaries include `hasBatchTracking` alongside the existing tracking flags. Physical intake endpoints are deferred; see [phase-2-task-3-tracking.md](phase-2-task-3-tracking.md).

## Treasury and bank accounts

Customer statement GET and transaction POST now enforce `customer-statement` screen access for cashiers in addition to session/CSRF rules. `GET /api/customers/{id}/statement` includes unfiltered `currentBalance` and movement `notes`; `closingBalance` still represents the selected period. The existing transaction API supports both inline statement actions (`increase`, `collection`); historical idempotency rules are unchanged. Overflow returns 400 validation and logged database failures return 503 with retry identity preserved. See [customer-statement.md](customer-statement.md).

`POST /api/suppliers/{id}/payments` now requires `treasuryAccountId` and effective `supplier-payment` permission plus the session/CSRF checks. It withdraws the amount from that account atomically with supplier settlement and invoice allocations; responses/history include `treasuryAccountId` and `treasuryMovementId`. Omitting invoice IDs automatically allocates by due date (invoice date fallback), then creation timestamp. Reads reflect allocated `paidAmount`/`remaining`. Missing source returns 400, insufficient funds/source conflict returns 409 with a `treasury_*` code, and logged database failures return 503 while preserving retry identity. Existing financial rows are not retroactively charged. See [supplier-payment-treasury.md](supplier-payment-treasury.md).

Supplier Accounts extends the existing `POST /api/suppliers/{id}/invoices` with optional `operationKey` (required by the new UI). Identical actor-bound requests replay the original invoice; changed supplier/payload/actor or a key owned by another financial operation returns `409 operation_conflict`. Invoice creation, the linked immutable supplier ledger entry and payable/credit projection are atomic. `GET /api/suppliers/{id}/invoices` additionally returns `documentStatus`, `returnedAmount` and return-adjusted nonnegative `remaining`. Purchase drafts cannot receive payments; payment DTOs select either `invoiceId` or `purchaseInvoiceId`. New debt invoice and payment inputs may use exact decimal text. See [supplier-accounts.md](supplier-accounts.md).

Cash purchase drafts now require `treasuryAccountId`; credit drafts require it to be null. Invoice reads include `treasuryAccountId`, `treasuryAccountName`, and nullable `treasuryMovementId`. `POST /api/purchases/{id}/post` atomically withdraws the full total from that account with stock receipt/FIFO, supplier settlement and audit. Missing account/funds return a `treasury_*` conflict and leave the draft/funds/stock unchanged. Purchase Management screen access permits account lookup and purchase-bound payment without granting manual treasury mutation permissions. Historical posted invoices are not retroactively charged. See [purchase-treasury.md](purchase-treasury.md).

All `/api/treasury/*` endpoints require the session cookie and return `{ success, data, error }`; mutations require `X-CSRF-Token`. Reading accepts any effective `accounts-list`, `account-deposit` or `account-withdraw` grant. Account management requires `accounts-list`; deposit and withdrawal each require their own screen grant. Administrators retain full access.

- `GET /api/treasury/accounts`: all nondeleted cash/bank accounts with `id`, `code`, `name`, `type` (`cash`/`bank`), `notes`, `version`, exact `balance` text and internal `balanceScaled`. The frontend displays the exact string.
- `POST /api/treasury/accounts`: `{ code, name, type, notes? }`; returns `201` with the zero-balance account.
- `PUT /api/treasury/accounts/{id}`: those fields plus current `version`; returns the saved account. This cannot edit money.
- `DELETE /api/treasury/accounts/{id}?version=N`: deletes only unused accounts, retaining the tombstone/audit; returns `{ deleted: true }`.
- `POST /api/treasury/deposit` and `POST /api/treasury/withdraw`: `{ accountId, amount, notes?, operationKey }`, with positive invariant amount text and at most two decimals. Returns `201` with `id`, `accountId`, `type`, exact `amount`/`balanceAfter` text, underlying scale-4 fields, UTC `createdUtc`, `notes`, and `replayed`. A replay returns the original historical post-balance; read accounts for current balances. Request hashes are internal.

Errors include `400 validation`, `404 not_found`, `409 duplicate_code`, `version_conflict`, `account_in_use`, `insufficient_balance`, `balance_overflow`, and `operation_conflict`, plus authentication/CSRF/screen denial. Database errors are logged and return Arabic `503 database_unavailable`; the client retains retry identity. See [treasury.md](treasury.md) for atomicity and integration boundaries.

## Product catalog

All catalog endpoints return the existing `{ success, data, error }` envelope, require an authenticated cookie, use effective screen access for cashiers, and require `X-CSRF-Token` on mutations. `salePrice` is required; `purchasePrice` is nullable and represents a reference/default acquisition cost, not inventory average cost. Both non-null monetary inputs are non-negative invariant decimal strings with at most two fractional digits and are stored in the scale-4 integer representation; they are never JSON binary-floating numbers. Product detail responses return `purchasePrice: null` when the cost is unknown.

- `GET /api/catalog/products`: bounded `page`/`pageSize` (maximum 100), `search`, exact `categoryId`, nullable `isActive`, and optional `includeArchived`. Each item also returns ordered `sizeValues` and `colorValues`, active `variantCount`, and persisted `hasExpiryTracking`, `hasSerialTracking`, and `hasImeiTracking` flags. Global feature disablement does not erase these saved summaries.
- `GET /api/catalog/products/{id}`; `POST /api/catalog/products`; `PUT /api/catalog/products/{id}`.
- `PUT /api/catalog/products/{id}/state`; `POST /api/catalog/products/{id}/archive` (administrator only).
- `GET|POST /api/catalog/categories`; `PUT /api/catalog/categories/{id}`. Writes are administrator-only.
- `GET|POST /api/catalog/units`; `PUT /api/catalog/units/{id}`. Writes are administrator-only.
- `GET /api/catalog/migration-issues` (administrator only).
- `GET /api/catalog/products/{id}` returns the product detail aggregate, including effective capability state, attribute values, product units/conversions, variants, SKUs, and barcode history.
- `GET /api/catalog/attributes?kind=all|system|custom&includeInactive=false` returns global size/color/custom attributes and values. Administrator-only CSRF-protected writes are `POST /api/catalog/attributes`, `PUT /api/catalog/attributes/{id}`, `POST /api/catalog/attributes/{id}/values`, and `PUT /api/catalog/attribute-values/{id}`.
- `GET /api/catalog/barcodes/lookup?code=...` performs authenticated scanner lookup and returns the product, variant, unit, rational conversion, effective prices, and a non-sellable reason when archived/inactive/retired. It requires the effective `barcode-scanning` capability.

Product create/update accepts an optional `configuration` object containing capability keys, attribute value assignments, product units (`numerator`/`denominator`), variants, per-variant SKUs, and multiple barcodes. Writes are atomic and administrator-only when configuration is supplied. Existing default variants remain compatible with simple Task 2.1 products.

Create product requires an `operationKey`. Reusing it with the same canonical request returns the first product; reusing it for different data returns HTTP 409 `operation_key_conflict`. Updates require `version`; stale writes return HTTP 409 `version_conflict`. Other stable codes include `invalid_category`, `invalid_unit`, `duplicate_category`, `duplicate_unit`, `category_cycle`, `review_required`, `archived`, `screen_forbidden`, and `invalid_csrf`.

## General settings endpoints

- `GET /api/settings/company`: authenticated company profile read.
- `PUT /api/settings/company`: administrator + CSRF protected company profile update.
- `GET /api/settings/general`: authenticated effective language/date/time/currency/tax settings.
- `PUT /api/settings/general`: administrator + CSRF protected validated update.
- `GET /api/settings/database-info`: administrator-only local path, size, migration count/latest name, journal mode, and foreign-key state. It cannot modify files.

All responses use the standard `{ success, data, error }` envelope. The only supported `languageCode` is `ar`, and `decimalPrecision` must be `2`; financial display is fixed to two digits while quantity formatting remains independent. Invalid formats, currency codes, precision, tax rates, email addresses, and inconsistent tax flags return `400 validation`. Database information returns no connection string or credentials.

All endpoints return `{ "success": true, "data": ... }` or `{ "success": false, "error": { "code": "...", "message": "..." } }`. Login, current-user restoration, and logout use the HttpOnly SameSite `alkhayal_session` cookie. JSON properties use camelCase.

- `GET /api/system/health` returns `{ status, utc, version }`.
- `POST /api/auth/login` accepts `{ username, password }`; success returns `{ id, username, displayName, role, csrfToken }` and sets the session cookie. Unknown users and invalid passwords return the same HTTP 401 credential error. A valid password for a disabled account returns the disabled-account response.
- `GET /api/auth/me` returns the same safe profile and current CSRF token for a valid, non-expired server-side session. Invalid or expired sessions return HTTP 401; expired records are deleted.
- `GET /api/auth/me/screen-access` returns `{ role, screenIds, generatedUtc }` after combining authentication, role, explicit cashier grants, administrator-only registry metadata, and effective feature state.
- `POST /api/auth/logout` requires the session cookie plus `X-CSRF-Token`. A missing or invalid token is rejected; success invalidates the session and expires the cookie.
- `GET /api/business-activities` requires an authenticated session and returns the active registry ordered by default priority. Each item includes `key`, `arabicName`, `description`, `defaultPriority`, `isActive`, and `suggestedCapabilities`.
- `GET /api/business-activities/selected` requires an authenticated session and returns `{ isConfigured, primaryActivityKey, activityKeys }`.
- `GET /api/business-activities/recommendations` requires an authenticated session. With no query it evaluates the saved selection; `?activityKeys=clothing,footwear` previews an unsaved selection. It returns deduplicated recommendations, source activity keys, Arabic reasons, newly recommended keys, recommendations that no longer apply, and preserved administrator override keys.
- `PUT /api/business-activities/selected` requires an authenticated `administrator` session and `X-CSRF-Token`. The body is `{ activityKeys, primaryActivityKey, applyRecommendations }`. It rejects unknown/inactive keys and a primary key outside the selection. Saving replaces only selection metadata; it does not delete business data. Recommendations are applied only when explicitly requested and never overwrite `administrator` capability rows.
Feature endpoints require authentication:

- `GET /api/features` returns stable catalog metadata for all core/optional modules and product capabilities.
- `GET /api/features/effective` returns resolved `modules`, `capabilities`, source/recommendation metadata, dependencies, and `generatedUtc`.
- `PUT /api/features/modules/{key}` and `PUT /api/features/capabilities/{key}` accept `{ isEnabled }`; administrator role and `X-CSRF-Token` are required. Unknown/core changes return 400 and dependency conflicts return 409.
- `POST /api/features/recommendations/preview` accepts `{ activityKeys }` and returns a read-only effective preview.
- `POST /api/features/recommendations/apply` accepts `{ activityKeys }`, requires administrator plus CSRF, applies dependency-complete recommendations, and preserves administrator overrides.

User-management endpoints require an authenticated administrator. Mutations additionally require `X-CSRF-Token`: `GET/POST /api/users`, `GET/PUT /api/users/{id}`, `PUT /api/users/{id}/status`, `POST /api/users/{id}/reset-password`, and `GET/PUT /api/users/{id}/screen-permissions`. They return 400 for validation/role/screen errors, 401 for missing sessions, 403 for cashier or CSRF failures, 404 for missing users, and 409 for duplicate usernames or last-active-administrator protection. Passwords and hashes are never returned.

Static frontend files, including `frontend/data/screens.json`, are served from the same OWIN origin with `Cache-Control: no-store, no-cache, must-revalidate`, `Pragma: no-cache`, and an expired response. This keeps the shell scripts and route registry on one deployment version in persistent WebView2 profiles.

Other business-screen operations do not yet have HTTP contracts: their UI state is explicitly in-memory and must not be interpreted as durable server behavior. Customer records and customer payments are exceptions: customer management endpoints persist customer data in SQLite.

- `GET /api/customers` returns the authenticated user's customer records from SQLite.
- `POST /api/customers` creates a customer; `PUT /api/customers/{id}` updates one; `DELETE /api/customers/{id}` deletes one. All writes require the session cookie and `X-CSRF-Token`. Customer codes are unique. The customer management list and add/edit/delete actions use these endpoints; other business screens remain session-only unless explicitly implemented.

Customer creation without a code allocates the next available `CUS-` numeric code in the database write transaction and returns it in the customer response. Existing codes are unchanged; explicitly supplied codes remain supported for existing API clients. Concurrent writers are serialized by SQLite and the unique code constraint.

`GET /api/suppliers?search=...&page=1&pageSize=25` returns `{items,totalCount,page,pageSize}`, ordered by name and ID. Search matches name, code, contact or phone. The existing unpaged request remains available to dependent screens. `GET /api/inventory/balance-page?warehouseId=1&search=...&page=1&pageSize=25` returns a page of warehouse balance rows with FIFO completeness, searching product name, active SKU or active barcode. Each row represents a variant and batch; counts refer to balance rows. Both page sizes are bounded to 100.
- `POST /api/customers/{id}/transactions` (`type` of `increase`/`collection`/`reduction`, positive `amount` with at most two decimal places — larger precision is rejected with 400 `validation`, never silently rounded; the ledger stores it scaled to 4 decimal places, `occurredOn` as `yyyy-MM-dd`, optional `notes` of at most 1000 characters, required `operationKey` ≤120 chars) records an idempotent customer-ledger transaction and updates `Customers.Balance` in one SQLite transaction. An identical retry of the same operation key returns the first transaction again with `replayed: true`. Reusing the key with a changed amount/type/date/notes or as a different customer returns HTTP 409 `operation_key_conflict` (same convention as sales/purchasing/catalog/inventory) and changes nothing. Notes are compared exactly as submitted: `null` is normalized to the empty string on both sides, but leading/trailing whitespace is never trimmed, so a whitespace-only change is a different request. Collisions with rows written by other financial paths are also rejected, decided from stored ownership metadata only — no key prefix is reserved (a manually chosen operation key may start with `CP-` or `sale-` and still replays identically whenever it matches this posting path's own row): sales invoice/payment/return rows populate the `Reference`, `SalesInvoiceId`, or `SalesReturnId` columns and carry a `RequestHash` that differs from the `OperationKey`; customer-payment rows are identified by an existing `CustomerPayments` row whose `Reference` equals the `OperationKey`, queried in the same transaction (the flow's ledger row keeps its original insert, which does not populate `Reference`); unrelated `opening`/`legacy_payment` ledger rows were never written by this posting path. Validation errors return 400 (`validation`); missing customers return 404 (`not_found`).
- Suppliers are also persisted. All endpoints require the session cookie; writes also require `X-CSRF-Token`. Legacy supplier invoices/payments remain stored in their original tables. New integrated purchasing and supplier-ledger monetary inputs permit at most two fractional digits, persist exact scale-4 integers, and use `yyyy-MM-dd` dates.
  - `GET /api/suppliers` lists suppliers with `payable` (currently owed) and `paid` (sum of payments). `POST /api/suppliers` creates one (optional opening `payable`); `PUT /api/suppliers/{id}` updates identity/contact fields only and never changes `payable`; `DELETE /api/suppliers/{id}` returns `409 supplier_in_use` when the supplier has invoices or payments.
  - `GET /api/suppliers/{id}/invoices` lists the supplier's invoices with `total`, `paidAmount`, `remaining`, and `status`. `POST /api/suppliers/{id}/invoices` (`invoiceNumber?`, `invoiceDate`, `dueDate?`, `total`, `notes?`) records a credit invoice and increases `payable` in one SQLite transaction. Invoice numbers are unique per supplier; a blank number is auto-generated (`SI-…`).
  - `POST /api/suppliers/{id}/payments` (`invoiceId?`, `purchaseInvoiceId?`, `amount`, `paymentDate`, `method`, `account?`, `notes?`, `operationKey`) records an idempotent scale-4 supplier-ledger payment. The two invoice IDs are mutually exclusive. It updates the supplier projection in the same transaction and checks invoice/supplier outstanding amounts. `account` is an optional text reference only; this endpoint does not post to a cash, bank, or treasury ledger.
  - `GET /api/suppliers/{id}/ledger` returns immutable supplier-ledger history; `GET /api/suppliers/{id}/statement?from=&to=` calculates opening, debit/credit movements, and closing balance from the unified ledger.
- Integrated purchasing routes require an authenticated user with purchasing screen access; mutations additionally require CSRF. `GET /api/purchases?supplierId=&from=&to=` lists invoices; `GET /api/purchases/{id}` reads one; `POST /api/purchases/drafts` creates a draft; `PUT /api/purchases/{id}` edits a draft; `POST /api/purchases/{id}/post` publishes it with an `operationKey`. Posting requires a valid draft version and invokes the shared inventory/FIFO post logic in the same SQLite transaction as invoice status/audit and supplier-ledger entries. Posted invoices are immutable. Draft line totals multiply scale-6 quantity by the scale-4 internal price and finalize once to the nearest piastre; taxes/discounts are not applied. Read DTOs include formatted decimal strings so JavaScript does not sum unsafe JSON integers.
- Purchase returns use `GET /api/purchases/{id}/returnable-lines?warehouseId=`, `GET /api/purchases/{id}/returns`, and `POST /api/purchases/{id}/returns` (`warehouseId`, explicit `returnMode` = `cash_refund|supplier_credit`, `operationKey`, and original invoice line IDs/quantities/physical units). Return posting restricts FIFO to the original receipt origin, including transferred layers, and atomically records inventory, return lines/variance, audit, and the matching supplier-ledger adjustment. `cash_refund` is a recorded supplier-account classification only; it does not create a treasury movement.

## Phase 2 / Task 2.4 inventory API

Authenticated routes under `/api/inventory`: `GET/POST /warehouses`, `GET/PUT /warehouses/{id}`, `GET /products`, `GET /products/{id}`, `GET /balances`, `GET /movements`, `GET /tracking?identifier=`, `POST /post`, `POST /counts`, `GET /counts/{id}`, `POST /counts/{id}/post`, `POST /counts/{id}/cancel`, `POST /documents/{id}/reverse`, `GET /integrity`, and `POST /integrity/rebuild`. All mutations require the session CSRF header; warehouse management, reversals, and integrity administration require administrator role. Other inventory routes require existing `warehouses-list` screen access. Query pages are bounded to 100 rows. Posting requires an internally generated stable `operationKey`, document `type`, warehouse, and product-unit/variant lines with decimal-string quantity. `reason` is optional and defaults to the operation-specific Arabic audit description. Positive intake requires explicit decimal-string `unitCost` per selected unit; `manual_receipt` also requires explicit decimal-string `salePrice` per selected unit. Neither price comes from a catalog fallback. Both inputs are nonnegative with at most two fractional digits and are persisted at scale 4. Retail price updates only the selected variant in the same transaction. Balance DTOs expose the effective variant `salePriceScaled`, `costBasisComplete`, `unresolvedLayerId`, and `hasReconciledCostBasis`; movement DTOs include `relatedWarehouseName`. Historical `valueScaled` on an unresolved balance is retained for audit and must not be displayed as confirmed FIFO cost. Count DTOs include lot/expiry labels and `serialTracked` for conditional correction fields. New administrator-only `POST /cost-basis/reconcile` accepts `{ operationKey, layerId, expectedVersion, unitCost, evidence }` under session/CSRF protection. It creates a documented opening cost basis only when its total equals the retained ledger value. Conflicts include `unresolved_cost_basis`, `legacy_value_mismatch`, and `fifo_integrity`. See [inventory-fifo.md](inventory-fifo.md) for legacy limitations and exact retry/rounding semantics. Conflicts include `operation_key_conflict`, `insufficient_stock`, `stale_count`, `batch_required`, and `identifier_not_in_stock`. See [inventory-ledger.md](inventory-ledger.md) for transaction and reversal rules.

## Sales invoices, collections, and returns (Phase 5)

- `GET /api/sales?search=&from=&to=` returns the latest 500 persisted invoices.
- `GET /api/sales/{id}` returns the invoice and saved line snapshots.
- `POST /api/sales/drafts` creates a versioned draft; `PUT /api/sales/{id}` updates a draft only.
- `POST /api/sales/{id}/post` accepts `{ operationKey }` and atomically posts the invoice and a `manual_issue` inventory document through the shared FIFO transaction path.
- `POST /api/sales/{id}/payments` accepts `{ amount, method, operationKey, occurredOn, notes? }` for an idempotent collection on a posted credit invoice. Methods are `cash`, `card`, or `transfer`.
- `POST /api/sales/{id}/returns` accepts `{ operationKey, reason, lines: [{ invoiceLineId, quantity, serials? }] }`. Each line is capped at the unreturned quantity. The transaction restores stock and original FIFO layer lineage, writes the return, refunds cash already received, and applies any eligible remainder as a customer credit adjustment.

Draft lines contain `variantId`, `productUnitId`, `quantity` (up to six decimals), `unitPrice` and optional line `discount` (EGP, at most two decimals). The invoice includes `customerId`, `warehouseId`, `invoiceDate`, `paymentMode` (`cash` or `credit`) and optional invoice `discount`. Credit requires a customer. The server confirms active product, variant, sale unit and current catalog price during save, applies persisted tax settings, and recalculates totals. Configured batch/expiry and serial/IMEI identifiers are required and checked against inventory at posting. Posting returns a conflict for insufficient stock, unresolved FIFO cost, stale draft, or a reused operation key with conflicting data. Payment and return routes require session/CSRF protection and the corresponding cashier screen permission; administrators retain access. Customer statements include invoice and return references. These ledger events do not post to treasury/cashbox. Receipt/reprint is browser thermal print output and does not claim confirmation of printer hardware state.
# Stabilization Part 1: sales cancellation and inventory valuation

`POST /api/sales/{id}/delete-draft` accepts `{operationKey}` and hides an eligible draft from normal history. The draft and its audit remain in storage; no inventory or customer ledger entry is reversed. `POST /api/sales/{id}/cancel` accepts `{operationKey,reason}`. An eligible unpaid credit sale gains a `canceled` projection in the sales list/detail, an immutable cancellation record, a reversing stock document with FIFO cost layers, and a customer `reduction` ledger entry in one SQLite transaction. Both calls return the normal `{success,data,error}` envelope. An identical retry returns `data.replayed=true`; a changed request with the same key returns `operation_key_conflict` (409). Posted cash sales, invoices with payments or returns, tracked units, and ambiguous later customer collections return a specific 409 conflict; they remain unchanged.

`GET /api/inventory/valuation?warehouseId={id}[&productId={id}]` returns an on-demand aggregate: `costValue`, `potentialSellingValue`, and `estimatedGrossMargin` as invariant-culture decimal strings with four places, plus completeness flags and variant count. A null amount means the source data is incomplete or inconsistent; clients must not treat it as zero. Values are for remaining FIFO layers, current selling prices, and the selected warehouse. The margin is potential, not realized profit.

# Stabilization Part 2: Touch POS reads and discount input

`GET /api/inventory/products?posWarehouseId={id}&page={n}&pageSize={n}[&search=...][&categoryId={id}]` is the bounded Touch POS browse request. It requires sales-read access and an active warehouse. It returns active, unarchived, ready stock products with an active variant and sale unit, the selected warehouse's aggregate `availableQuantityScaled`, and normal `CatalogPage` pagination (`totalCount`, `page`, `pageSize`). Ordering is net base-unit quantity sold over the previous 30 UTC days, with valid returns subtracted, then product name and ID. Canceled invoices are excluded. Search covers name, SKU, and barcode. The normal product-list endpoint behavior is unchanged when `posWarehouseId` is absent.

`GET /api/inventory/categories` returns active categories under sales-read access. `GET /api/customers/search?query=...` returns at most 20 active customers matching name, code, or phone; it does not transfer the whole customer directory to Touch POS.

Touch POS converts an entered invoice percentage (0–100 with at most two decimal places) to one fixed, two-decimal discount amount before `POST /api/sales/drafts` or `PUT /api/sales/{id}`. The existing sales service recalculates tax and total from that amount and posts the customer ledger as before. The persisted invoice stores the monetary discount, so reopening it presents fixed-amount mode.

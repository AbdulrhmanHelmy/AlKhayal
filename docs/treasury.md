# Treasury and bank accounts

The treasury module has exactly three visible destinations: `accounts-list` (قائمة الخزنة والبنك), `account-deposit` (إيداع رصيد), and `account-withdraw` (سحب رصيد). The directory contains all saved cashboxes and bank accounts, their balances, and create/edit/delete dialogs. Old add/balance/movement routes are hidden compatibility redirects to the directory and no longer provide independent workflows.

Accounts have a unique normalized code, name, cash/bank type, notes and optimistic version. New accounts start at zero; their first balance is a recorded deposit. Used accounts cannot change type or be deleted, even after withdrawal leaves zero. Unused accounts can be deleted from the directory; their database rows are tombstoned and their audit retained. Codes remain reserved after deletion. Editing metadata never changes money. Cashiers need `accounts-list` to manage accounts and separate deposit/withdraw screen grants to post each direction. Any of the three grants, Purchase Management access, or Supplier Accounts access, permits reading accounts for selection. Administrators retain full access.

`TreasuryService` owns validation, money conversion, request hashing and transaction-snapshot rules. `ITreasuryStore` is the Application port; `SqliteTreasuryStore` owns parameterized persistence and the writer transaction. The host composes these with `TreasuryController`, which translates session, effective screen access, CSRF and HTTP contracts. Migration `024_treasury.sql` is additive and runs at normal startup against the configured database. It creates no sample accounts, imports no mock balances and changes no existing financial rows.

Amounts are positive invariant strings with at most two decimals, converted exactly to signed 64-bit scale-4 integers. Withdrawals cannot exceed the balance; overflow is rejected. Immutable deposits minus withdrawals derive balances. A writer lock precedes reading the balance, so concurrent withdrawals cannot spend the same funds. Movement, account version and append-only audit commit together; a late failure rolls everything back. Movement/audit update/delete triggers and restrictive foreign keys retain history.

Posting requires a unique `operationKey`. Identical replay returns the original movement ID, amount, timestamp and historical balance after that movement with `replayed: true`. Reusing a key for another account, direction, amount, notes or authenticated actor returns `409 operation_conflict`. Canonical hashing uses length-prefixed fields and exact scaled money: `10.1` and `10.10` are equivalent. Request hashes never appear in responses. Retry state stays in the workspace draft. An uncertain network/5xx result freezes its fields and retries the same command/key, including after a tab switch. Successful posting displays movement number, amount, local timestamp and balance after the movement, then refreshes current balances.

Cash purchase posting now withdraws from its explicitly selected account in the same transaction as the stock receipt, supplier settlement and invoice audit; see [purchase-treasury.md](purchase-treasury.md). Supplier settlement now also withdraws from its selected account and allocates on-account payments to invoices; see [supplier-payment-treasury.md](supplier-payment-treasury.md). Expense vouchers now withdraw atomically from the selected cashbox/bank; see [expenses.md](expenses.md). New cash sales deposit atomically in إيراد الوردية; see [sales-shift-revenue.md](sales-shift-revenue.md). Cash returns now have atomic treasury effects described in [returns-management.md](returns-management.md). Later customer collections and cancellations retain their independent boundaries. Transfers, bank reconciliation, treasury reversal/editing and an independent history screen are outside this scope. Immutable movement rows remain available for auditing in SQLite.

## Verification and compatibility

### Retained legacy migration 019

Some deployed databases record `019_treasury.sql` (absent from the current source tree) with a differently shaped `TreasuryAccounts`, `TreasuryTransactions` and `TreasuryAccountAudit`. Before executing pending 024, `TreasuryLegacyCompatibility` recognizes that recorded schema and renames its account table to `LegacyTreasuryAccounts019` inside the same migration transaction. SQLite preserves/retargets the original foreign keys and triggers. Migration 024 then creates the current schema and the adapter imports account IDs and exact historical movement amounts, actors and timestamps. Original bank details, account state, transfer links, references, old operation hashes and audit remain in the retained original tables. `TreasuryLegacyImports` provides immutable one-to-one source links. Opening/transfer-in become deposit entries; withdrawal/transfer-out become withdrawal entries, with their original type/date/reference in the import description. Original operation keys remain reserved and cannot replay as new commands. Previously inactive accounts remain hidden/blocked; their original inactive state and all balances remain retained, without automatic reactivation.

Unknown schemas, normalized-code collisions, incompatible sub-piastre values, overflow or invalid/negative historical balances abort the entire 024 transaction without rounding, dropping tables or altering the original rows. Historical SQL scripts are unchanged. `TreasuryLegacyMigrationTests` covers empty/populated 019, bank details, original immutable audit, transfer balances, inactive retention, repeat startup, new writes after import, and atomic rollback of incompatible legacy histories. The operator database was read only: a SQLite backup snapshot in the workspace successfully migrated twice and passed integrity/foreign-key checks. Initial startup failure was `table TreasuryAccounts already exists` because fresh-only tests had missed this deployed schema.

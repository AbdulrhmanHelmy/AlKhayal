# Phase 2 / Task 2.3 tracking foundation

Product tracking is configuration stored in `ProductCapabilityAssignments` by the existing aggregate product create/edit transaction. `expiry-dates` requires `batch-tracking`; `imei-tracking` requires `serial-numbers`. Application expands dependencies from `FeatureRegistry` before persistence. Data rejects direct writes with missing tracking parents. Global availability is checked only for new assignments, so a later global disable does not erase an existing assignment. Product version checks guard edits. Basic products need no tracking selection.

The catalog summary derives batch, expiration, serial and IMEI flags from persisted assignments, including assignments whose global capability is now disabled. Badges describe configuration only. The product form does not request a physical lot, expiration date, serial, or IMEI.

`TrackingIdentityRules` is a pure future intake validation contract. Lot identity is `(VariantId, normalized lot number)` and expiration is a separate `yyyy-MM-dd` business date for that lot. Serial and IMEI normalized identifiers will be unique globally across both types, including history. Text normalization is Unicode Form KC, trim, invariant uppercase, and excludes controls. Lot numbers are at most 80 characters; ordinary serials at most 120. IMEI is exactly 15 ASCII digits with a Luhn checksum. Other formats require an explicit later policy. A physical unit can have one serial and multiple IMEIs; each identifier links to that same unit and never adds quantity.

No Task 2.3 migration creates physical identities: the current schema already persists all four configuration assignments and variant identities. Creating batch/serial rows now without a posted ledger movement would permit orphan physical stock claims. Task 2.4 must add batch, physical unit, identifier, warehouse, and movement-link tables together, and insert source document, movement, identities, derived balance and audit event in one SQLite transaction. It must enforce required lot/expiry at intake, whole-unit serialized quantities, duplicate identity rejection, FEFO allocation, immutable posted history, auditable expiry and reversal transitions, and a history-aware guard before tracking is downgraded. Existing products have no posted inventory history yet; Task 2.4 must add that guard before enabling posting.
